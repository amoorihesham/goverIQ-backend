# Implementation Plan: Voting & Minutes

**Branch**: `005-voting-minutes` | **Date**: 2026-05-17 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `specs/005-voting-minutes/spec.md`

## Summary

Build the **Votes** module (`src/modules/votes/`) and the **Minutes** module
(`src/modules/minutes/`) — the 6th and 7th domain modules — following the
flat-route, factory-function conventions of `org` / `roles` / `members` /
`invitions` / `meetings`. Twelve Fastify route handlers cover the governance
cycle: 5 vote endpoints (create, list, detail, cast ballot, close) and 7 minutes
endpoints (create, read, edit, attach resolution, finalize, append correction,
export).

A pure, unit-testable utility — `votes/utils/outcome.ts` — computes a vote
outcome from a ballot tally, the quorum threshold, and the affirmative option,
with no Fastify or DB import. Minutes export renders a compliance-grade **PDF**
via `pdfkit`, isolated in `minutes/utils/pdf.ts`. Two new error codes
(`VOTE_CLOSED`, `MINUTES_FINALIZED`) join the shared registry; `DUPLICATE_BALLOT`,
`MEETING_HAS_OPEN_VOTES`, `CONFLICT`, and `INVALID_STATE_TRANSITION` already
exist. One new shared pre-handler, `requireMembership`, gates the identity-only
minutes read. Eight audit events emit transactionally.

This feature applies **one additive schema migration** — a single `ADD COLUMN`
on `votes` for the designated affirmative option (research [Decision 2](./research.md));
no table is created and no existing column is altered. The
`IN_PROGRESS → COMPLETED` open-votes guard is **already wired** in
`meeting.service.ts` (it counts `OPEN` votes); this feature adds no
meeting-module code — only an integration test proving the guard now actively
blocks once real votes exist. The module satisfies all 24 functional
requirements (FR-401 … FR-424) and all 10 success criteria (SC-401 … SC-410).

> **Two spec Assumptions are superseded by planning decisions confirmed with the
> user** (recorded in [research.md](./research.md)): the assumption of "no
> column changes" is overridden by [Decision 2](./research.md) (add
> `votes.affirmative_option`), and the implicit no-new-dependency assumption is
> overridden by [Decision 9](./research.md) (`pdfkit` for PDF export). Both are
> deliberate, user-approved choices.

## Technical Context

**Language/Version**: TypeScript 6.x on Node.js 24 LTS (unchanged)
**Primary Dependencies**: Fastify 5.8.x, Drizzle ORM, Zod 4.x, Pino,
`fastify-type-provider-zod` — all installed. **One new runtime dependency**:
`pdfkit` (MIT-licensed, actively maintained) plus its `@types/pdfkit`, both
pinned to exact versions per the Technical Standards.
**Storage**: existing `votes` / `vote_eligibility` / `ballots` / `minutes` /
`minutes_resolutions` / `minutes_corrections` Postgres tables. **One additive
migration** — `ALTER TABLE votes ADD COLUMN affirmative_option text NOT NULL`,
generated by `drizzle-kit generate` (`src/db/migrations/0003_*.sql`). The
migration runs against an empty `votes` table (Phase 4 has not shipped), so
`NOT NULL` with no default is non-destructive. The feature also reads `meetings`,
`meeting_attendees`, `memberships`, and `organizations.quorum_threshold`.
**Testing**: Vitest (unit + integration). Integration helpers at
`tests/integration/helpers/db.ts` need `truncateVoteTables()` and
`truncateMinutesTables()` additions.
**Target Platform**: Linux server / Node.js 24 (containerized, stateless).
**Project Type**: Backend web service — modular monolith. `src/modules/votes/`
and `src/modules/minutes/` are the 6th and 7th domain modules.
**Performance Goals**: All endpoints p95 < 200 ms (Constitution IV, SC-410). The
hot paths — vote list (meeting-scoped keyset query on `votes_meeting_status_idx`),
ballot cast (PK + unique-index lookups + one insert), close (one grouped tally
query + bounded eligibility count + conditional update), minutes read (three
index-backed queries) — are fixed-shape and index-backed against ≥ 1,000
meetings. PDF rendering on export is bounded by one minutes document's content.
**Constraints**: Every state-changing handler MUST run inside `withTx` so
`emitAudit(tx, …)` joins the same transaction (FR-404, FR-423, Constitution
audit invariant). The eligibility snapshot is insert-only and MUST never be
mutated after vote creation (FR-403). Per-member ballot choices MUST never
appear in any read/list/export response or audit payload (FR-407). Permission
resolution is per-request from the DB — no caching. All routes are reachable
only when org onboarding is `COMPLETE` (FR-422).
**Scale/Scope**: 12 protected routes, 1 pure utility module, 1 PDF render
module, 1 new shared pre-handler, 2 new error codes, 1 additive migration,
8 audit events, ≈ 17 new source files plus tests.

Add matching `AppError.voteClosed()` and `AppError.minutesFinalized()` factory

Decision 5 / 11).

### Outcome Computation (votes/utils/outcome.ts — pure)

```ts
export type VoteOutcome = 'QUORUM_NOT_MET' | 'TIED' | 'PASSED' | 'FAILED';

interface OutcomeInput {
  options: string[]; // ≥ 2 distinct (FR-402)
  optionCounts: Record<string, number>; // ballot count per choice
  totalEligible: number; // ≥ 1 (FR-403)
  totalCast: number;
  quorumThreshold: number; // 0..1, Number(organizations.quorum_threshold)
  affirmativeOption: string; // votes.affirmative_option
}

export function computeOutcome(input: OutcomeInput): { outcome: VoteOutcome; winner: string | null } {
  const { options, optionCounts, totalEligible, totalCast, quorumThreshold, affirmativeOption } = input;

  if (totalCast / totalEligible < quorumThreshold) {
    return { outcome: 'QUORUM_NOT_MET', winner: null };
  }
  const counts = options.map((o) => optionCounts[o] ?? 0).sort((a, b) => b - a);
  if (counts[0] === counts[1]) return { outcome: 'TIED', winner: null };

  const winner = options.find((o) => (optionCounts[o] ?? 0) === counts[0])!;
  return { outcome: winner === affirmativeOption ? 'PASSED' : 'FAILED', winner };
}
```

Pure: no Fastify, no DB, no clock. `totalEligible ≥ 1` is guaranteed by FR-403,
so there is no division by zero. The full algorithm and `result_summary` jsonb
shape are fixed in [contracts/vote-outcome.md](./contracts/vote-outcome.md). The
service builds `optionCounts` from a single `GROUP BY` query and assembles
`result_summary` around the returned `{ outcome, winner }`.

### Pre-handler Chains

Every route composes
`identityRequired → attachOrgId → requireOnboardingStep('complete') → <auth>`,
where `<auth>` is `requirePermission(key)` for all routes **except** minutes
read, which uses the new `requireMembership` (FR-419 — identity only, any org
member, no permission key; research Decision 10):

```ts
// src/shared/http/pre-handlers/require-membership.ts — new pre-handler
export async function requireMembership(request: FastifyRequest) {
  const { userId, orgId } = contextFromRequest(request);
  if (!userId || !orgId) throw AppError.create('UNAUTHORIZED');

  const [membership] = await db
    .select({ roleId: memberships.roleId, isOwner: roles.isOwner, permissions: roles.permissions })
    .from(memberships)
    .leftJoin(roles, eq(memberships.roleId, roles.id))
    .where(and(eq(memberships.userId, userId), eq(memberships.orgId, orgId)))
    .limit(1);
  if (!membership) throw AppError.create('FORBIDDEN', 'Not a member of the organization');

  request.orgMembership = {
    roleId: membership.roleId,
    isOwner: membership.isOwner ?? false,
    permissions: membership.permissions || [],
  };
}
```

It is `requirePermission` without the final key check — it confirms the caller
is a member of the path org and stops there.

### Vote Creation & Eligibility Snapshot (FR-401 … FR-404)

Inside one `withTx` block:

1. Load the meeting (scoped to org); `404` if absent. Meeting status must be
   `IN_PROGRESS` → else `INVALID_STATE_TRANSITION` (FR-401).
2. Resolve the eligible set (FR-403):
   - `eligibleMemberIds` null/omitted → the meeting's current `meeting_attendees`.
   - explicit list → every id must already be a `meeting_attendees` row for this
     meeting; any miss rejects the whole request.
   - the resulting set MUST be non-empty → else `VALIDATION_ERROR`.
3. Insert the `votes` row (`status='OPEN'`, `affirmative_option`, `outcome` and
   `result_summary` null).
4. Bulk-insert one `vote_eligibility` row per eligible membership.
5. `emitAudit(tx, { event: 'vote.created', … })`.

`affirmativeOption` is validated to be one of `options` by a Zod cross-field
refine and re-checked in the service. `options` must have ≥ 2 distinct entries
(Zod refine).

### Eligibility & Ballot Casting (FR-405 / FR-406)

`requirePermission` attaches `{ roleId, isOwner, permissions }` but **not** the
membership id. Ballot eligibility is keyed by `vote_eligibility.member_id`
(→ `memberships.id`), so `vote.service.ts` resolves the caller's membership id
itself from `(userId, orgId)` via the `memberships_user_org_unique` index
(research Decision 9-adjacent), then checks for a `vote_eligibility` row.

Ballot casting, inside `withTx`:

1. Load the vote (scoped to meeting + org); `404` if absent.
2. Vote `status !== 'OPEN'` → `VOTE_CLOSED` (422).
3. Caller's membership not in `vote_eligibility` → `FORBIDDEN` (403).
4. `choice` not in `vote.options` → `VALIDATION_ERROR` (400) — runtime check, the
   option set is per-vote data (research Decision 6).
5. `INSERT` the ballot. The `ballots_vote_voter_unique` `(vote_id, member_id)`
   index rejects a second ballot; the service catches the unique violation via
   `isUniqueViolation` and throws `AppError.duplicateBallot()` — race-free,
   including the concurrent-double-submit edge case (research Decision 7).
6. `emitAudit(tx, { event: 'ballot.submitted', payload: { data: { voteId } } })`
   — the payload **omits the choice** to keep ballots confidential (FR-407).

### Vote Close (FR-408 / FR-409)

Inside one `withTx` block:

1. Load the vote; `404` if absent.
2. Tally: `SELECT choice, COUNT(*) FROM ballots WHERE vote_id = ? GROUP BY choice`.
3. Count `vote_eligibility` rows (`totalEligible`) and total ballots
   (`totalCast`).
4. `computeOutcome(...)` with `Number(organizations.quorum_threshold)`.
5. Conditional update so concurrent closes resolve to one winner (research
   Decision 12):
   ```ts
   const [closed] = await tx
     .update(votes)
     .set({ status: 'CLOSED', outcome, resultSummary, closedAt: new Date() })
     .where(and(eq(votes.id, voteId), eq(votes.status, 'OPEN')))
     .returning();
   if (!closed) throw AppError.conflict('Vote is already closed');
   ```
6. `emitAudit(tx, { event: 'vote.closed', payload: { before: { status:'OPEN' },
after: { status:'CLOSED', outcome } } })`.

### Meeting-completion guard (FR-410) — no code change

The `IN_PROGRESS → COMPLETED` guard is **already implemented** in
`meeting.service.ts` (it counts `votes` rows with `status='OPEN'` and throws
`MEETING_HAS_OPEN_VOTES`). It was correct but dormant only because no vote rows
existed. This feature adds **no meeting-module code** — `vote-close.test.ts`
adds an integration test: create an `OPEN` vote, confirm completion is rejected
with `MEETING_HAS_OPEN_VOTES`, close the vote, confirm completion then succeeds.

### Minutes Lifecycle (FR-412 … FR-418)

Status guards are checked inline — two states do not warrant a state-machine
module (research Decision 7). Error mapping follows
[data-model.md](./data-model.md):

- **Create** — meeting must be `COMPLETED` (else `INVALID_STATE_TRANSITION`);
  `minutes_meeting_id_unique` rejects a second document → handler's default
  unique-violation translation yields `CONFLICT` (FR-412). Inserts `status='DRAFT'`;
  emits `minutes.created`.
- **Edit summary/notes** — allowed only in `DRAFT`; on a `FINALIZED` doc →
  `MINUTES_FINALIZED`. Emits `minutes.updated`.
- **Attach resolution** — allowed only in `DRAFT` (else `MINUTES_FINALIZED`); the
  referenced vote must belong to this meeting and be `CLOSED`, else rejected.
  Inserts a `minutes_resolutions` row; emits **no** audit event (research
  Decision 13).
- **Finalize** — allowed only in `DRAFT`; sets `status='FINALIZED'` and
  `finalized_at`; a re-finalize hits a `FINALIZED` doc → `CONFLICT`. Emits
  `minutes.finalized`.
- **Append correction** — allowed only in `FINALIZED`; on a `DRAFT` doc →
  `INVALID_STATE_TRANSITION`. Inserts a `minutes_corrections` row; emits
  `minutes.correction_added`.

### Minutes Export (research Decision 9)

`GET …/export` loads the meeting, minutes, resolutions, and corrections, passes
them to `renderMinutesPdf()` (`minutes/utils/pdf.ts`, built on `pdfkit`), emits
`minutes.exported`, and replies with the PDF — bypassing the success envelope,
as a file download:

```ts
reply
  .header('content-type', 'application/pdf')
  .header('content-disposition', `attachment; filename="minutes-${meetingId}.pdf"`)
  .send(pdfBuffer);
```

`renderMinutesPdf()` imports `pdfkit` only — no Fastify, no DB — so it is
isolated and testable; export correctness is verified by
`minutes-read-export.test.ts` (asserts `application/pdf` and a valid `%PDF`
header).

### Transaction & audit contract (8 events)

| Operation         | Writes                               | Audit event                 |
| ----------------- | ------------------------------------ | --------------------------- |
| create vote       | `votes` + `vote_eligibility` inserts | `vote.created`              |
| cast ballot       | `ballots` insert                     | `ballot.submitted`          |
| close vote        | `votes` conditional update           | `vote.closed`               |
| create minutes    | `minutes` insert                     | `minutes.created`           |
| edit minutes      | `minutes` update                     | `minutes.updated`           |
| attach resolution | `minutes_resolutions` insert         | _(none — research Dec. 13)_ |
| finalize minutes  | `minutes` update                     | `minutes.finalized`         |
| append correction | `minutes_corrections` insert         | `minutes.correction_added`  |
| export minutes    | _(read-only)_                        | `minutes.exported`          |

Every state-changing service method opens one `withTx` block performing the
write(s) and the `emitAudit(tx, …)` call together; a rollback discards both
(FR-404, FR-423, Constitution audit invariant). Audit payloads are specified in
[data-model.md](./data-model.md); the `ballot.submitted` payload never carries
the choice (FR-407).
